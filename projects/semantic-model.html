Power BI Semantic Model

A star schema semantic model built on top of the warehouse from my report ingestion pipeline, with calculation groups handling time intelligence and rolling trend periods. It's written in TMDL, the text format that Power BI, Fabric, and SSAS all read, so the whole model can be reviewed on GitHub like any other code.

The model

Two fact tables share one date table. Station activity has one row per station per day (62,312 rows from January 2022 through September 2026), and the weather table has one row per day of Chicago O'Hare readings going back to 1959.

A couple of the design choices are worth explaining:

  • Weather is its own fact table. Joining the weather onto the station rows would be simpler, but each day's rainfall would then be added up once per station (36 times). Keeping it separate and relating it to Date means the precipitation totals stay correct no matter what's on the rows.
  • The weather categories live on Date. Precipitation Category and High Temperature Band describe the day, so slicing ridership by weather goes through the same single relationship as everything else, with no bidirectional filtering needed.

Comparing a partial year to the prior year

The bike share data runs through September 30, 2026. A standard prior-year calculation at the year level compares those nine months against all twelve months of 2025, which makes ridership look like it fell off a cliff:

PeriodTrips2026 vs this
2026 (Jan to Sep)829,697
2025, full year (standard prior year)1,045,266-20.6%
2025, Jan to Sep (this model's PY)834,199-0.5%

The Date table has an Is Reported column marking every date up to the last reported day, and the PY, YoY, and YoY % items only shift the dates that have actually been reported (the approach SQLBI describes for hiding future dates):

CALCULATE (
    SELECTEDMEASURE (),
    CALCULATETABLE (
        SAMEPERIODLASTYEAR ( 'Date'[Date] ),
        'Date'[Is Reported] = TRUE ()
    )
)

The rolling windows in Trend Period anchor on the last reported date for the same reason, so "Rolling 28 Days" for 2026 measures the last 28 days of actual data rather than the empty weeks at the end of December.

Measure notes

Each measure in the model has a description covering the grain it's built for and what its total row means. A few examples:

MeasureWhat the total row means
Average Ride MinutesWeighted by trips (total riding time over total trips), so a quiet station doesn't count as much as Navy Pier.
Average Daily TripsTrips divided by days reported, so months and weather categories with different numbers of days compare fairly.
Trips vs Dry Days %Compared against dry days under the same other filters. Meant for month, season, or weather category; blank for a single day unless that day was dry.
Hot Days per YearDays at or above 90°F divided by the years in context, so a partial decade compares fairly with a full one.
YoY / YoY %Blank when either period has no value, rather than showing a fake 100% change.

How it was checked

A PowerShell script deploys the model to SQL Server Analysis Services as an empty, temporary database, checks every column, measure, and calculation item for errors, evaluates all 17 measures under every combination of the two calculation groups (476 in total), and then deletes the database again.

To be clear about what that covers: it proves the model and its DAX are valid, not that the numbers are right. The figures on this page were calculated in SQL against the same views the model reads. Refreshing the model against the data is the next step.

About the data

Weather data is from NOAA NCEI's Global Historical Climatology Network – Daily, a U.S. government work in the public domain. Lakefront Bike Share is fictional, and its ridership is simulated from the real O'Hare weather for each day, so any weather effect on ridership reflects the simulation, not a finding.
