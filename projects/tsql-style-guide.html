T-SQL Style Guide

These are the formatting and coding conventions I use for SQL Server. Each rule comes with a before/after example and an explanation of why it's there, since the standards are enforced through code review rather than a linter, and a reviewer needs a reason to point to.

  • T-SQL
  • SQL Server
  • Code review

Why bother with a style guide

Once a data warehouse grows past a few hundred SQL files, most of your time goes to reading code rather than writing it, and a lot of that code was written by someone else (or by you, two years ago, at 4:45 on a Friday). A shared style means every file reads the same way, which makes reviews faster and mistakes easier to spot.

Some of these rules prevent actual bugs, and some are just house style; I've labeled which is which. For the house-style rules, picking one way and sticking with it matters more than which way you pick.

All examples use a made-up bike-share warehouse: trips, stations, riders, and daily weather.

01 Uppercase keywords, bracketed names

Uppercase keywords separate the language from your data at a glance. Brackets on every schema, table, column, and alias mean names like [Date], [User], or [Rain (in)] always work. With one consistent look, find-and-replace across a thousand files is reliable.

Built-in functions with no schema, like CAST, ISNULL, and GETDATE, stay unbracketed.

SELECT
    [DimDate].[Date]
    , [FactWeather].[PrecipitationInches]
FROM
    [Warehouse].[FactWeather]
    INNER JOIN [Warehouse].[DimDate] ON [FactWeather].[DateKey] = [DimDate].[DateKey];

02 Clause keywords and indentation

SELECT, FROM, WHERE, GROUP BY, and ORDER BY sit at column 0 on their own lines. Everything under them is indented 4 spaces, never tabs. Reading down the left edge gives you the shape of the query before you read a single column.

03 Leading commas

With trailing commas, commenting out the last column in a list breaks the query. With leading commas, any column except the first can be commented out, added, or moved by touching a single line, which also means code review diffs show one changed line instead of two.

The trade-off is that commenting out the first column breaks the query instead, but in practice the first column is almost always a key that never moves.

04 Descriptive aliases

Single-letter table aliases make the reader keep a lookup table in their head. Using the table's own name means every column reference says where it comes from, and a search for [FactTrip].[ finds every use. When the same table joins twice, the alias names its role.

Column aliases drop AS and are written for the person reading the output, because final columns often land directly in a report.

05 Grouping WHERE conditions

SQL Server evaluates AND before OR, which is an easy thing to forget and a common source of wrong numbers. The query below was meant to return member trips in two cities, but it actually returns member trips in Chicago plus every trip in Evanston. Following the guide forces the grouping to be written out explicitly, which makes this kind of bug much easier to catch.

06 CASE expressions

A CASE with a single condition can stay on one line. Anything longer gets one WHEN per line so the conditions read top to bottom, with the alias on the END line.

SELECT
    [FactTrip].[TripID]
    , CASE
          WHEN [FactTrip].[DurationMinutes] < 10 THEN 'Short'
          WHEN [FactTrip].[DurationMinutes] < 45 THEN 'Medium'
          ELSE 'Long'
      END [Trip Length]
FROM
    [Warehouse].[FactTrip];

07 CTEs

Each CTE gets a bracketed name describing what it holds, with its body indented between parentheses at column 0. Additional CTEs start with a leading comma, the same as columns do.

WITH [DailyTrips] AS
(
    SELECT
        CAST ( [FactTrip].[StartTime] AS DATE ) [TripDate]
        , COUNT(*) [Trips]
    FROM
        [Warehouse].[FactTrip]
    GROUP BY
        CAST ( [FactTrip].[StartTime] AS DATE )
)
, [DailyWeather] AS
(
    SELECT
        [DimDate].[Date] [TripDate]
        , [FactWeather].[PrecipitationInches]
    FROM
        [Warehouse].[FactWeather]
        INNER JOIN [Warehouse].[DimDate] ON [FactWeather].[DateKey] = [DimDate].[DateKey]
)
SELECT
    [DailyTrips].[TripDate] [Trip Date]
    , [DailyTrips].[Trips]
    , [DailyWeather].[PrecipitationInches] [Rain (in)]
FROM
    [DailyTrips]
    LEFT JOIN [DailyWeather] ON [DailyTrips].[TripDate] = [DailyWeather].[TripDate]
ORDER BY
    [DailyTrips].[TripDate];

House style: CAST, CONVERT, ISNULL, COALESCE, NULLIF, and TRY_CAST get spaces inside their parentheses, which keeps nested conversions readable.

08 Stored procedure header

Every stored procedure starts with the same two settings, and both of them prevent real problems:

  • SET NOCOUNT ON stops the "rows affected" messages that confuse some client tools and SSIS packages.
  • SET XACT_ABORT ON makes any runtime error roll back the whole transaction. Without it, the delete below could succeed, the insert fail, and the fact table be left empty for that day.
CREATE PROCEDURE [Warehouse].[uspLoadFactTrip]
(
    @LoadDate DATE
    , @BatchID INT
)
AS
BEGIN;
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    BEGIN TRANSACTION;

    DELETE FROM
        [Warehouse].[FactTrip]
    WHERE
        [FactTrip].[LoadDate] = @LoadDate;

    INSERT INTO [Warehouse].[FactTrip]
    (
        [TripID]
        , [StartStationID]
        , [StartTime]
        , [LoadDate]
        , [BatchID]
    )
    SELECT
        [TripImport].[TripID]
        , [TripImport].[StartStationID]
        , TRY_CAST ( [TripImport].[StartTime] AS DATETIME2(0) )
        , @LoadDate
        , @BatchID
    FROM
        [Staging].[TripImport];

    COMMIT TRANSACTION;
END;

09 Semicolons

SQL Server already requires semicolons in a few places: MERGE has to end with one, and so does the statement right before a CTE or a THROW. Microsoft also lists leaving them out as deprecated. Ending every statement with one means nobody has to remember which cases require it.

Why usp and not sp_? SQL Server checks the master database first for any procedure starting with sp_. That costs a lookup on every call and risks colliding with a system procedure.

Schemas by layer make the data flow visible in every name: raw files land in Staging, modeled data lives in Warehouse, reports read from Analytics, and load history goes to Audit.

How it's enforced

There's no linter involved; the standards are enforced in code review, and having the reasoning written down for each rule keeps those reviews from getting subjective. I've also turned the guide into a set of instructions for the AI coding assistant I use, so any SQL it drafts already follows the guide by the time it gets to review.
